# Deploying the live demo (free)

The public demo runs on **Render** (free web service, Docker) with a **Neon** (free) Postgres
database. Both have free tiers with no card required at the time of writing; free tiers change, so
check their pricing pages first.

Why this split: Render's own free Postgres expires after 30 days, Neon's free database does not.
Render builds straight from GitHub and redeploys on every push to `main`.

## What runs

- Render builds the `Dockerfile`'s last stage (`prod`) and runs `bin/start.sh`:
  1. `migrate` (there is no separate release step on the free plan, so the container does it),
  2. `seed_demo --reset` when `DEMO_RESET_ON_START=true`: wipes **all** data and reseeds,
  3. `gunicorn` on the `$PORT` Render assigns, `$WEB_CONCURRENCY` workers.
- Free services sleep after ~15 idle minutes, and waking takes about a minute. The **Keep awake**
  workflow (`.github/workflows/keep-awake.yml`) pings `/livez/` every 10 minutes so the demo stays
  online 24/7. One always-on service uses ~744 of the workspace's 750 free hours a month, so a
  second free service in the same Render workspace would run out of hours: put it in another
  workspace, or turn the heartbeat off. `/livez/` skips the database so Neon can still suspend;
  `/healthz/` (Render's health check) does query it. GitHub can delay scheduled runs, and it turns
  scheduled workflows off after 60 days without commits (re-enable them in the Actions tab).
- The demo data resets on every start, which now means every deploy or restart, not every visit.
- `DEMO_MODE=true` shows the demo accounts on the login page with `DEBUG` off, blocks password
  changes, and keeps the owner out of `/admin/` (see "Public demo safety" in the README).

## One-time setup

1. **Neon:** sign in with GitHub at neon.tech, create a project (`restocore`, region close to
   Render's, e.g. AWS Singapore). Copy the **connection string** (starts with `postgresql://`,
   ends with `?sslmode=require...`). Keep it private.
2. **Render:** sign in with GitHub at render.com → **New → Blueprint** → pick this repository.
   Render reads `render.yaml` and asks for `DATABASE_URL`: paste the Neon connection string.
   `DJANGO_SECRET_KEY` is generated by Render; everything else is preset in `render.yaml`.
3. Wait for the first deploy (build + migrate + seed, a few minutes). Open
   `https://<service>.onrender.com/healthz/` → `ok`, then the home page.

## Environment variables (set by render.yaml)

| Variable | Value | Why |
| --- | --- | --- |
| `DATABASE_URL` | Neon connection string (dashboard only) | Database; never committed |
| `DJANGO_SECRET_KEY` | generated by Render | Signing key; never committed |
| `DJANGO_DEBUG` | `False` | Never debug in public |
| `DJANGO_HTTPS` | `true` | HTTPS redirect, secure cookies, HSTS (Render terminates TLS) |
| `DJANGO_STATIC_MANIFEST` | `true` | Fingerprinted, cacheable static files |
| `DEMO_MODE` | `true` | Public-demo behaviour (see above) |
| `DEMO_RESET_ON_START` | `true` | Fresh demo data on every start / wake-up |
| `DEMO_PASSWORD` | `restocore-demo` | Shared demo password (shown on the login page) |
| `WEB_CONCURRENCY` | `2` | Workers that fit the free 512 MB instance |
| `DJANGO_TIME_ZONE` | `Asia/Manila` | Opening hours and bookings in local time |

`ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS` pick up Render's hostname automatically from
`RENDER_EXTERNAL_HOSTNAME`. The read-only API stays off (no `RESTOCORE_API_TOKEN`).

## Rehearse locally

The same image and start script, pointed at the Compose database:

```
docker build --target prod -t restocore:prod .
docker compose exec db psql -U restocore -d postgres -c "CREATE DATABASE render_sim"
docker run --rm --network restocore_default -p 127.0.0.1:8090:10000 -e PORT=10000 \
  -e DJANGO_SECRET_KEY=local-rehearsal-only -e DJANGO_ALLOWED_HOSTS=127.0.0.1 \
  -e DATABASE_URL="postgresql://restocore:restocore@db:5432/render_sim?sslmode=disable" \
  -e DJANGO_STATIC_MANIFEST=true -e DEMO_MODE=true -e DEMO_RESET_ON_START=true restocore:prod
```

Then open <http://127.0.0.1:8090/>.

## Before every deploy

CI already runs `python manage.py check --deploy` with HTTPS settings on every push. A red CI run
means: do not deploy; read the failing step's log first.
