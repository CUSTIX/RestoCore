# Runbook

What to do when something needs doing on the live demo. Setup from scratch is in
[deploy.md](deploy.md); security controls are in [SECURITY.md](../SECURITY.md).

Live: <https://restocore.onrender.com> (Render free web service, Singapore) with a Neon free
Postgres database. All data is fake.

## Quick checks

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://restocore.onrender.com/livez/    # app is up (no DB)
curl -s -o /dev/null -w "%{http_code}\n" https://restocore.onrender.com/healthz/  # app + database
```

`/livez/` is Render's health check, so a suspended Neon database never makes Render restart the app.
`/healthz/` failing while `/livez/` passes means the database is unreachable or the password is wrong.

## Deploy

Push to `main`. Render deploys only after CI passes (`autoDeployTrigger: checksPass` in
`render.yaml`; the Blueprint syncs that file on every push).

- Before pushing: `pytest`, `ruff check .`, `ruff format --check .` and
  `python manage.py check --deploy` (see deploy.md, "Before every deploy").
- Avoid deploying around **04:00 Manila**: that is the nightly demo reset, and a deploy also resets
  the data on start. Two resets at once are safe (they run one after the other) but slow the start.

## Roll back

In Render: service **restocore**, then **Events**, pick the last good deploy, **Rollback**.
Then revert the bad commit on `main` (`git revert <sha>`), so the next push does not bring it back.

## Rotate a secret

| Secret | Where it lives | How |
|---|---|---|
| Database password | Neon and Render `DATABASE_URL` | Neon: project, **Roles**, `neondb_owner`, **Reset password**. Build the new URL (same host, new password), test it (`psql "<url>" -c "select 1"`), then paste it into Render, **Environment**, `DATABASE_URL`, **Save, rebuild, and deploy**. The app cannot open new connections between the reset and the save, so do both within a few minutes. |
| `DJANGO_SECRET_KEY` | Render (generated by the Blueprint) | Render, **Environment**, generate a new value, save. Everyone is signed out. |
| `RESTOCORE_API_TOKEN` | Render and the MCP client's environment | Set a new random value (16+ characters) in both. |
| `GEMINI_API_KEY` | Render | Create a new key in Google AI Studio, replace it in Render, delete the old key. |

Secrets never go in the repo, logs or screenshots. Only `.env.example` is committed.

## Restore data

The demo has no real data, so the recovery is to reseed:

```bash
# Render shell, or locally against the same DATABASE_URL
python manage.py seed_demo --reset    # wipes ALL data and reseeds, in one transaction
```

The container also reseeds on every start and nightly when `DEMO_MODE=true` and
`DEMO_RESET_ON_START=true`.

If real data were ever stored (not the case today), take a backup first:

```bash
pg_dump "<DATABASE_URL>" --format=custom --file restocore.dump     # backup
pg_restore --clean --no-owner --dbname "<DATABASE_URL>" restocore.dump   # restore
```

Neon also keeps a short history: **Branches**, **Restore** to a point in time (free plan: a limited
window).

## Logs

Render: service **restocore**, **Logs**. The access log has method, path, status, size and time,
never query strings (they can carry personal data). Errors are logged with a timestamp, level and
logger name.

## Cold starts and the heartbeat

The free service sleeps after 15 minutes without traffic. `.github/workflows/keep-awake.yml` pings
`/livez/` every 10 minutes. GitHub may delay scheduled runs, so a cold start (about a minute) is
still possible. Check **Actions**, **Keep awake** if the site is often slow. A second free pinger
(cron-job.org or UptimeRobot, every 5 minutes) is the fallback.
